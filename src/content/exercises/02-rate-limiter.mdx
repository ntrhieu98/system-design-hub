## Mục tiêu

Thiết kế hệ thống giới hạn tần suất (rate limiting) chống lạm dụng API. Bạn chọn thuật toán, giải thích được vì sao, và xử lý được trường hợp nhiều instance cùng đếm một client.

## Yêu cầu

### Yêu cầu chức năng

1. **Đếm request theo client**: nhận diện client bằng IP hoặc API key
2. **Áp giới hạn**: từ chối request vượt ngưỡng đã cấu hình
3. **Cho phép burst**: chấp nhận burst tạm thời tới một ngưỡng tối đa
4. **Nạp lại**: token nạp lại với tốc độ không đổi theo thời gian

### Yêu cầu phi chức năng

1. **Độ trễ**: bước kiểm tra phải xong trong dưới 1ms
2. **Phân tán**: chạy được trên nhiều instance
3. **Chính xác**: không được cho qua nhiều hơn hoặc chặn nhầm quá nhiều
4. **Quan sát được**: có metric về tốc độ hiện tại, số lần từ chối, trạng thái bucket

## Token bucket

### Tham số

- **rate**: tốc độ nạp (token/giây)
- **capacity**: số token tối đa bucket giữ được
- **burst**: burst tối đa cho phép (thường bằng capacity)

### Cách hoạt động

1. Bucket khởi đầu đầy (capacity token)
2. Mỗi request tiêu 1 token
3. Token nạp lại với tốc độ `rate` token/giây
4. Bucket đầy thì ngừng nạp
5. Bucket rỗng thì từ chối request

### Mô hình toán

```
tokens(t) = min(capacity, tokens(t-1) + rate × Δt)
allowed    = tokens(t) > 0 && consume_token()
```

### Ví dụ cấu hình

- rate = 10 token/giây (duy trì 10 req/giây)
- capacity = 100 token (burst tới 100 request)
- Bình thường: 10 req/giây
- Burst: tối đa 100 request liên tiếp
- Sau burst: 10 giây để nạp đầy lại

## Ba cách triển khai

### 1. Chỉ trong bộ nhớ (một instance)

```python
rate_limits = {}  # client_id -> {tokens, last_refill}

def check_rate(client_id, rate, capacity):
    now = time.time()
    if client_id not in rate_limits:
        rate_limits[client_id] = {"tokens": capacity, "last_refill": now}

    limit = rate_limits[client_id]
    # Nạp token theo thời gian đã trôi qua
    elapsed = now - limit["last_refill"]
    add_tokens = elapsed * rate
    limit["tokens"] = min(capacity, limit["tokens"] + add_tokens)
    limit["last_refill"] = now

    if limit["tokens"] > 0:
        limit["tokens"] -= 1
        return True   # cho qua
    return False      # từ chối
```

- Cache trong bộ nhớ cho client nóng
- Redis làm nguồn đúng cho client lạnh hoặc khi cần nhất quán giữa các instance

## Tích hợp API gateway

### Response 429

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 3600
{
  "error": "rate_limit_exceeded",
  "limit": 10,
  "remaining": 0,
  "reset": 1704067200
}
```

### Header nên trả

- `X-RateLimit-Limit`: tổng số request được phép trong chu kỳ
- `X-RateLimit-Remaining`: số request còn lại trong chu kỳ hiện tại
- `X-RateLimit-Reset`: mốc epoch khi bộ đếm reset

## Quyết định thiết kế

### 1. Khoá đếm theo cái gì

**Quyết định:** theo client (IP hoặc API key)

- Ưu điểm: cô lập từng client, dễ hiểu
- Nhược điểm: nhiều user sau NAT dùng chung IP sẽ bị tính là một client
- **Chọn:** theo client, vì giới hạn nhắm đúng đối tượng

### 2. Chặn ở đâu

**Quyết định:** ở API gateway / tầng edge

- Ưu điểm: chặn sớm, tiết kiệm tài nguyên backend
- Nhược điểm: thêm một hop, gateway phải đủ năng lực
- **Chọn:** chặn ở edge

### 3. Tính tất định

**Quyết định:** nạp token tất định để kết quả đoán trước được

- Rate limiter phải cho cùng kết quả với cùng chuỗi request
- **Chọn:** công thức nạp tuyến tính theo thời gian, không dùng random
