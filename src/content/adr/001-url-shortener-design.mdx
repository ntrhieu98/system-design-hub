## Bối cảnh

Chúng tôi đang xây dựng dịch vụ rút gọn URL tương tự TinyURL hoặc Pastebin trong khuôn khổ bài tập system design Module 1.4. Hệ thống cần xử lý:
- Rút gọn URL dài thành mã ngắn
- Chuyển hướng từ mã ngắn về URL gốc
- Thông lượng đọc cao (ước tính 10K QPS)
- Độ trễ thấp cho redirect
- Schema lưu trữ đơn giản

## Yếu tố quyết định

### 1. Thiết kế API
**Quyết định:** Sử dụng RESTful API với endpoints:
- `POST /shorten` — Tạo URL ngắn
- `GET /{code}` — Chuyển hướng về URL gốc

**Phương án thay thế:** GraphQL API
- Ưu điểm: Query linh hoạt, single endpoint
- Nhược điểm: Quá phức tạp cho CRUD đơn giản, client implementation phức tạp hơn
- **Chọn:** REST vì đơn giản và cacheable

### 2. Hash Function & Xử lý Collision
**Quyết định:** Sử dụng hash function ổn định (FNV-1a hoặc tương tự) với base62 encoding, implement collision resolution qua retry

**Phương án thay thế:** UUID-based short codes
- Ưu điểm: Không collision guaranteed
- Nhược điểm: Codes dài hơn (~12 chars vs ~6 chars), ít thân thiện với người dùng
- **Chọn:** Hash-based cho codes ngắn hơn (6 chars base62 = 62^6 = 56,8 tỷ tổ hợp, 35,7 bits)

### 3. Schema Lưu trữ
**Quyết định:** Simple key-value store
- Table: `urls(code PRIMARY KEY, original_url TEXT, created_at TIMESTAMP)`
- Index trên `code` cho O(1) lookups

**Phương án thay thế:** Full relational schema với normalized tables
- Ưu điểm: Linh hoạt hơn cho attributes tương lai
- Nhược điểm: Không cần thiết cho use case đơn giản
- **Chosen:** Simple KV cho overhead tối thiểu

### 4. Scaling lên 10M URLs / 10K QPS
**Quyết định:** Sharding strategy
- Sử dụng consistent hashing trên short code để distribute across N shards
- Mỗi shard hoạt động độc lập
- Monitor load và thêm shards khi cần

## Hệ quả

### Tích cực
- Đơn giản, dễ implement và maintain
- Performance cao với hash-based lookup
- Scale horizontal qua sharding

### Tiêu cực
- Collision resolution có thể gây latency spike
- Không hỗ trợ custom alias (có thể thêm sau)
- Analytics cơ bản (chỉ click count)

### Rủi ro
- Hash collisions ở scale lớn → cần bloom filter
- Single point of failure nếu không replicate
- Data loss nếu không backup

## Tham khảo
- Alex Xu "System Design Interview" Ch.8: Design a URL Shortener
- Base 62 conversion: 62^7 = ~3.5 trillion (đủ cho 365 billion URLs trong 10 năm)
- 301 redirect vs 302 redirect: trade-off giữa server load và analytics
