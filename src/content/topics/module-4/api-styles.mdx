<p>Ba kiểu giao tiếp API khác nhau ở <span class="kw">tầng vận chuyển</span>, <span class="kw">cách mô tả dữ liệu</span> và <span class="kw">cách tiến hoá schema</span>. Câu hỏi phỏng vấn không phải "cái nào tốt hơn" mà "hệ thống này cần gì". Trả lời "gRPC nhanh hơn nên dùng gRPC" là câu trả lời của người chưa từng vận hành gRPC trong trình duyệt.</p>

        <h3>REST — mặc định đúng cho API công khai</h3>
        <ul class="list-bullet">
          <li><strong>Khi nào chọn:</strong> API cho đối tác, cho mobile app đơn giản, cho bất cứ thứ gì cần cache qua CDN hoặc debug bằng <code>curl</code>.</li>
          <li><strong>Điểm mạnh bị đánh giá thấp:</strong> HTTP đã có sẵn cache, ETag, conditional GET, rate limit theo route, và mọi hạ tầng trên đời hiểu nó. Đây là giá trị vận hành, không phải giá trị kỹ thuật thuần.</li>
          <li><strong>Điểm yếu thật:</strong> over-fetching và under-fetching. Một màn hình phức tạp cần 5–7 endpoint, mỗi endpoint lại trả thừa field. Với mobile 3G đây là tiền thật.</li>
        </ul>

        <h3>GraphQL — khi client cần tự quyết định hình dạng dữ liệu</h3>
        <ul class="list-bullet">
          <li><strong>Khi nào chọn:</strong> nhiều client khác nhau (iOS, Android, web, smart TV) cùng đọc một graph; hoặc màn hình thay đổi liên tục tới mức không kịp thêm endpoint.</li>
          <li><strong>Cái bẫy N+1:</strong> mỗi field là một resolver. Query <code>user &#123; orders &#123; items &#125; &#125;</code> với 3 order sinh 1 + 1 + 3 = 5 query DB. Phải có <span class="kw">DataLoader</span> gộp theo batch, nếu không GraphQL chậm hơn REST.</li>
          <li><strong>Bảo mật:</strong> client có thể gửi query lồng 20 tầng làm sập server. Bắt buộc: giới hạn độ sâu, giới hạn độ phức tạp (cost analysis), tắt introspection ở production.</li>
          <li><strong>Cache:</strong> mọi query là POST nên CDN và HTTP cache vô dụng. Phải làm cache ở tầng application theo query hash, hoặc dùng persisted query (client gửi hash thay vì chuỗi).</li>
        </ul>

        <h3>gRPC — ngôn ngữ mặc định của nội bộ microservice</h3>
        <ul class="list-bullet">
          <li><strong>Khi nào chọn:</strong> service-to-service trong cùng VPC, cần latency thấp, cần streaming, hoặc cần hợp đồng chặt để không vỡ khi team khác deploy.</li>
          <li><strong>Vì sao nhanh hơn:</strong> Protobuf mã hoá nhị phân theo field number (không lặp tên field), parse nhanh hơn JSON nhiều lần; HTTP/2 cho phép multiplexing nhiều request trên một connection, header nén bằng HPACK. Payload nhỏ 3–10× là con số thường gặp.</li>
          <li><strong>Vì sao không dùng cho browser:</strong> browser không expose trailer của HTTP/2, mà gRPC dùng trailer để trả status. Phải có gRPC-Web và một proxy (Envoy, hoặc grpc-gateway) dịch. Đó là thêm một tầng phải vận hành.</li>
          <li><strong>Tiến hoá schema:</strong> đổi kiểu field, đổi số field, hoặc tái sử dụng số field đã xoá đều gây lỗi im lặng. Dùng <code>reserved 3, 5;</code> để chặn vĩnh viễn.</li>
        </ul>
